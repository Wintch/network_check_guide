# Case Study: The "ISP Shaping" That Was Actually a 3-Month-Old Local Watchdog Loop

A real, fully worked incident. Kept as a template for the next time something looks like
network shaping/instability but the cause turns out to be somewhere else entirely.

## Starting symptom

"Claude Code keeps connecting out and it's unclear how long a command should take to
complete — maybe my ISP is doing shaping." Two residential internet links were in play
(a dual-WAN setup); the first instinct was to test both for throttling/shaping.

## Step 1 — synthetic tests looked basically fine

`curl -w` timing loops to the real AI API endpoint (10 attempts, per-phase timing:
DNS/connect/TLS/TTFB) showed boring, low, consistent numbers (tens of ms). A naive
conclusion at this point would have been "network's fine, must be something else" —
**wrong**, because the problem was intermittent and short single-shot tests kept missing it.

## Step 2 — reading real, already-open connections (the actual breakthrough)

Instead of more synthetic tests, the live TCP connections already open to the API host were
read directly:

```bash
ss -tin dst <api-ip>
```

This immediately showed something a single curl never would: **among ~15-20 simultaneous
connections to the exact same server, some were perfectly clean (RTT 3-10ms, zero
retransmits) while others showed massive retransmission (tens of KB), collapsed congestion
windows (cwnd down to 1-4), and RTT spikes to 30-60ms with huge jitter** — all at the same
moment, to the same destination.

A 10-sample time series (one sample every 15 seconds, ~2.5 minutes total) confirmed this
wasn't a one-off: several connections showed **retransmitted bytes climbing continuously for
the entire observation window**, and RTT on specific flows jumping from ~4ms to ~35ms and
staying there for 75+ seconds before partially recovering.

**Interpretation at this point:** same server, same instant, wildly different per-flow
behavior — inconsistent with plain distance/congestion (which hits all flows evenly) and
suggestive of either per-flow ISP shaping, or a shared local resource periodically dying.
Full technique in `05_AI_WORKLOAD_AND_LATENCY.md`.

## Step 3 — an independent report changed the whole direction

An unrelated Claude Code session running on a different VM on the same LAN had, that same
day, produced its own incident report after noticing ping loss during routine work. That
report found something much more specific and damning:

```
ping -D -i1 to an external server: exactly 8-9 seconds of 100% loss, every ~35 seconds,
regular and repeating. Confirmed to happen already at the FIRST HOP (the LAN gateway),
before any traffic reaches the ISP. Ruled out as ISP-caused for that reason.
```

**Lesson:** an independent, high-resolution, first-hop measurement is worth more than a
sophisticated analysis of second- and third-hop symptoms. This single report reframed
everything that had been measured so far — the "per-flow shaping" pattern in step 2 was
consistent with a *periodic full local outage*, not shaping: different TCP flows simply had
in-flight data at different points in the 35-second cycle, making the damage look "per-flow"
from the outside.

## Step 4 — confirming scope and finding the mechanism

1. **Confirmed the pattern independently**, from a third, unrelated machine on the same LAN
   segment: `ping -D -i1 -c 140 <gateway>` showed the same ~9-second gaps every ~34-35
   seconds. Not host-specific — the whole LAN segment was affected.
2. **Went to the physical/bridge layer** on the router host serving that LAN segment:
   `dmesg` showed a specific USB-Ethernet NIC (serving the shared bridge for the entire LAN)
   **unregistering and re-registering itself on almost exactly the same ~35-second period.**
3. That NIC's re-enumeration cycle was traced to `systemctl list-timers` → an active
   **watchdog timer**, running every 30 seconds, whose job was: ping a fixed peer, and if it
   fails, reset the NIC via USB re-authorization.
4. **The watchdog's own log told the real story:** across its entire history (since
   deployment), it had logged **32 successful recoveries against 61,066 consecutive
   failures** — and grouping failures by date showed it worked fine (sporadic, real
   recoveries) for its first ~2 months, then on one specific day jumped to failing **every
   single cycle, every day, for the following 25 days straight**, right up to the moment of
   this investigation.
5. **Correlated that exact date** against other infrastructure history: it matched, to the
   day, a previous live network reconfiguration on the router VM that had briefly taken its
   interfaces down and back up (a separate, already-documented incident). That event is the
   prime suspect for whatever broke the watchdog's own health-check — most likely an
   ARP/bridge-table side effect — though the exact mechanism wasn't packet-captured to
   100% certainty. Documented as a strong correlation, not an unproven claim.
6. **Directly reproduced the watchdog's own failing check by hand** (`ping` from the
   router's LAN IP to its peer) — confirmed 100% loss, matching the log, and confirmed via
   `ip neigh` on both ends that ARP/MAC resolution itself was fine (ruling out a previously
   *suspected-but-unconfirmed* ARP-flux bug as the cause of this specific symptom, since that
   bug had separately already been fixed).

## Step 5 — the fix, and confirming it worked

The watchdog had not fixed anything in 25 days; it was actively causing an outage every 35
seconds. After explicit confirmation (**never disable a production watchdog silently** —
someone put it there for a real reason, even if it's now doing net harm), it was stopped and
disabled:

```bash
systemctl stop <watchdog>.timer
systemctl disable <watchdog>.timer
```

**Verification, not assumption:**
- Immediately after: `ping -D -i1 -c 120` to the gateway → **0% loss, zero gaps** (vs. 22%
  loss with regular gaps before).
- 8 minutes later, a longer run: `ping -D -i1 -c 480` → **480/480 received, 0% loss, zero
  gaps.**
- Re-checked the same live `ss -tin` connections to the AI API host that had shown chaos in
  Step 2 → all stable at 4-6ms, no retransmits, no RTT spikes.
- Confirmed no further NIC register/unregister events in `dmesg`, and the watchdog's own log
  stopped growing.

## What this confirms about method, for next time

1. **Diagnose closest to home first.** "ISP shaping" was the initial hypothesis and the
   hardest one to prove or disprove without disruptive tests (flipping WAN links). The real
   cause was found in minutes once the first hop was checked directly with a high-resolution
   ping — a completely non-disruptive, always-available check that should be step one, not a
   fallback.
2. **A per-flow-looking symptom can have a whole-link cause.** Don't jump to "shaping" or
   "per-connection policing" just because different simultaneous flows to the same
   destination look different — a periodic full outage produces exactly that appearance from
   the traffic layer.
3. **Independent, unrelated data points are gold.** The second VM's incident report — made
   for a completely different reason, by a different session — was the single piece of
   evidence that reframed the whole investigation. When two independent observations point
   at the same LAN, believe the LAN, not either individual, more complex theory.
4. **A watchdog's log is only useful if you check its success rate, not just its
   existence.** "There's a watchdog for this" is not the same as "the watchdog is working."
   Count `success` vs. `failure` over its full history before trusting it.
5. **Confirm the fix with the same rigor as the diagnosis.** A 2-minute clean ping right
   after a change can still be luck. An 8-minute clean run, plus re-checking the exact
   real-traffic connections that showed the original symptom, is what actually closes the
   loop.
6. **Ask before disabling something load-bearing-sounding, even when the data is
   overwhelming.** The watchdog existed for a real, previously documented reason (a genuine
   hardware quirk in the NIC it manages). Disabling it was clearly correct here, but it's a
   production change on shared infrastructure — worth one explicit confirmation, not a
   unilateral call, even under time pressure.
